# doc-mine

把一個專案的知識挖出來,寫成 `docs/` 下分類的 Markdown。**每一句敘述都有據**:句尾標來源,標不出來就標 `[UNVERIFIED]`。開工前先訪談使用者,問到使用者說「開始」。

## 流程

0. 掃一眼 — README + 頂層目錄,讓訪談問得出具體模組名;確定輸出位置
1. 訪談 — 一輪最多兩題,問到使用者說「開始」
2. 讀專案 — 小專案主線自己讀;大專案派 2–4 個 subagent 依區域分工
3. 寫文件 — `1x` 原理、`2x` 場景、`3x` 參考、`4x` 取捨;每句敘述帶標記
4. 回應 — `00-answers.md`:使用者以為的,逐條驗證對或錯
5. 收尾 — 開檔重看 `[src:]`、重開 `[doc:]`;寫 `90-unverified.md` 和 `README.md` 索引

## 核心原則:有據

敘述的依據只有三種——專案裡的檔案、官方文件、實際執行結果。命名、慣例、「通常是這樣」只是**線索**,拿來找證據用;找不到證據就寫 `[UNVERIFIED]` 並說明缺什麼。**寧可留白,不補猜。**

證據標記放在敘述句的句尾,一句一個;一句有兩個主張就拆成兩句。標記裡寫的就是證據本身:路徑和行號、URL、指令,或同一份文件裡的 `R` 編號。只有導覽句不加標記——它只介紹這份文件、指出去哪份檔案看。其他寫到專案的句子都是敘述,使用建議也算,標它依靠的專案行為。

| 標記 | 來源 | 例 |
|---|---|---|
| `[src: <path>:<line>]` | 專案內的檔案(原始碼、README、config) | `[src: src/main.rs:42]` |
| `[doc: <URL>]` | 官方網站、官方文件 | `[doc: https://example.com/docs/cli]` |
| `[run: <指令>]` | 實際執行過的指令 | `[run: rtk --version]` |
| `[UNVERIFIED]` | 三種都沒有,括號寫缺什麼 | `[UNVERIFIED](找不到寫入邏輯)` |

- `[doc:]` 只用本次用 WebFetch 實際開過的頁面。
- `[run:]` 只跑唯讀指令(`--version`、`--help`、列出、dry-run);會寫檔、安裝、連網的指令先問使用者再跑。
- `[run:]` 的指令和輸出一起貼進同一份文件。指令一行寫不下時,把指令和輸出貼成程式碼區塊、編號 `R1`、`R2`…,句尾寫 `[run: R1]`。

## 輸出

- **語言**:跟使用者對話的語言;使用者指定就依指定。
- **位置**:`docs/`;repo 用別的目錄名(例如 `doc/`)就跟它。那個目錄已經有專案自己的文件,就寫到它底下的 `mined/`,避免混在一起。
- **目標檔已存在**:步驟 0 就先問使用者要覆蓋還是換檔名,問完才往下做。

檔名是 `<編號>-<主題>.md`。十位數代表類別,照編號排就是閱讀順序:

| 編號 | 內容 | 只有一份時的檔名 |
|---|---|---|
| `00` | 訪談回應(步驟 4) | `00-answers.md` |
| `1x` | 技術原理:它怎麼運作 | `10-how-it-works.md` |
| `2x` | 應用場景:什麼時候用、怎麼搭配 | `20-use-cases.md` |
| `3x` | 操作參考:指令、參數、設定 | `30-reference.md` |
| `4x` | 設計取捨:為什麼這樣做,代價是什麼 | `40-design-tradeoffs.md` |
| `90` | 全部 `[UNVERIFIED]` 的清單(步驟 5) | `90-unverified.md` |

- 一類重點多就拆成多份:`x0` 用上表的檔名,當這類的總覽;`x1` 起依閱讀順序,檔名接主題,例如 `11-parser.md`、`12-storage.md`。
- 使用者說不要的類跳過,其他類的編號不變。
- 另寫一份 `README.md` 當索引(步驟 5)。

## 步驟 0 — 快速掃一眼(不深讀)

讀 README 和頂層目錄,目的有兩個:讓訪談問得出具體的東西(「這裡有 A、B、C 三個模組,哪個最想懂?」);依「輸出」節確定輸出位置。完成條件:能用一兩句說出這專案是什麼、分哪幾塊;輸出位置已確定。

## 步驟 1 — 訪談(問到使用者說「開始」)

一輪最多兩題,等回答再問下一輪。使用者答「不知道」就記下、換下一題,不追問。使用者說「開始」(或 start、go、可以了)就停,進步驟 2。使用者一開始就說「直接開始」「不用問」→ 跳過訪談,步驟 4 不產出。

依序問這五題,再依回答追問:

1. 你目前怎麼理解它?一兩句就好。
2. 你用它做什麼?或打算拿來做什麼?
3. 哪部分最想搞清楚?(用步驟 0 看到的模組名具體問)
4. 有沒有你「覺得應該是這樣,但沒確認過」的?
5. 有沒有不需要整理的部分?

第 4 題的答案是**查證重點**:每一條都要在步驟 4 給出有據的對或錯。

完成條件:使用者說「開始」。把訪談整理成一段**訪談摘要**——認知、用途、重點、待驗證清單、排除清單——留給步驟 2 和步驟 4 用。

## 步驟 2 — 讀專案

**分工判準**:專案小(單一模組、幾十個檔案內)→ 主線自己讀,不派 agent。專案大 → 派 **2–4 個** subagent,**依程式碼區域分工**(頂層目錄、模組),一個 agent 一個區域。**硬上限 4 個**,派滿就不再派。

派工 prompt 必帶:

- 訪談摘要(agent 看不到主對話)
- 負責的區域路徑
- 「核心原則:有據」整節(原樣貼過去)
- 輸出契約:**條列筆記**,每條句尾帶標記,不寫成文章。待驗證清單裡屬於這區域的項目逐條回答。
- 一句:「自己讀完直接回報,不再派 agent。」

主線收齊筆記後才開始寫。完成條件:每個區域都有筆記;待驗證清單每條都有人回答,或明確回報找不到。

## 步驟 3 — 寫分類文件

一份文件一個主題,依「輸出」節的位置和編號寫 `1x`–`4x`;依訪談決定哪類拆細、哪類跳過。完成條件:每一句敘述都有標記。

## 步驟 4 — 訪談回應 `00-answers.md`

一份獨立文件,放在同一個輸出目錄、排最前面,只回答訪談裡使用者提的東西:

- **你說的** — 訪談摘要
- **你問的** — 第 3 題逐項回答,附標記
- **你以為的 vs 實際上** — 第 4 題逐條:對就寫對,錯就寫實際上是什麼,都附標記;查不到就 `[UNVERIFIED]`

## 步驟 5 — 收尾

1. `00-answers.md` 裡每個 `[src:]` 都實際開檔看那一行;其他文件每份抽 5 條開檔看,有 1 條對不上就整份驗。內容對不上就改敘述或改標記。
2. 每個 `[doc:]` 用 WebFetch 再開一次;開不到或內容對不上就改成 `[UNVERIFIED]`。
3. 寫 `90-unverified.md`:每條 `[UNVERIFIED]` 一項,寫在哪份文件、缺什麼。一條都沒有就不寫這份。
4. 寫 `README.md` 索引:依編號列出每份文件,一行說它回答什麼。
5. 回報文件寫在哪、共幾份、`[UNVERIFIED]` 幾條。

完成條件:驗過的 `[src:]` 和 `[doc:]` 全部對得上;`90-unverified.md` 列出每一條 `[UNVERIFIED]`;`README.md` 列出每一份文件。
